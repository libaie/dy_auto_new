# 多分辨率元素定位：配置与上线指南

本次优化基于已合并的审查修复版本 `8dac313`，用于 AutoJS6 / Rhino ES5.1 设备脚本、FastAPI 服务端和 Vue 管理端。代码在独立分支交付；提交代码与更新生产服务器、手机脚本是不同步骤。

## 已实现的行为

| 环节 | 行为 |
| --- | --- |
| 语义定位 | 保留资源 ID、文本、描述、组合条件和链式查找；根据当前应用可见区域过滤候选，支持唯一语义锚点。无障碍节点的 bounds 直接按屏幕像素使用。 |
| 坐标换算 | 统一处理屏幕、应用区域、锚点区域和实际截图的坐标；读取显示尺寸、方向、密度、字体缩放和可观测窗口遮挡。 |
| 点击执行 | 定位点带几何签名和观测时间；执行前核验可见范围与新鲜度。延迟后的重试重新定位。 |
| 图片匹配 | `images.scale` 使用等比倍率；保留配置阈值，在限定区域和有限尺度候选中匹配，回收截图和模板资源。 |
| OCR | 只使用带位置的结构化结果；文字本身不是坐标。范围内存在多个匹配时返回失败，不再点击猜测位置。 |
| 横竖屏与分辨率变化 | 根据实时尺寸重新选配置，即使服务端配置修订号没有变化，也能刷新；网络失败时保留兼容配置并限频重试。 |
| 标定 | 根据实际观测的唯一目标裁图；纯坐标不参与自动标定。记录截图源尺寸、有效密度、来源选择器 ID/版本和目标抖音版本。 |
| 发送结果 | 评论、私信以观测到的界面变化确认结果；无确认时不计成功、不自动补一次回车。新设备的私信占用保持“发送待确认”，不会被旧的 30 分钟清理规则重新放行。 |

## 选择策略的顺序

优先为一个动作配置稳定的资源 ID、文本或描述；重复出现的文字应限定在正确容器内。若控件没有可用语义信息，再使用局部图片或已有的 OCR 降级。坐标适合作为明确配置的最后手段。

`priority` 越小越先尝试。此次不批量重排现有策略，以免改变已有动作的选择顺序。请检查旧配置是否把坐标策略排在更可靠的语义策略之前。

不同分辨率不一定意味着不同布局，同一分辨率也可能因为显示缩放、字体大小、输入法或抖音版本不同而产生不同布局。不要只按手机型号复制一套整屏坐标。

## 管理界面如何设置

在选择器管理页编辑一个动作的策略卡，可以设置以下字段：

- **坐标空间**：新建坐标策略默认使用应用可见区域比例。
- **显式点击偏移单位**：像素、dp 或目标尺寸比例。
- **定位区域**：限定在屏幕、应用可见区域或锚点区域的一部分。
- **锚点**：单条文本、资源 ID、描述或类名条件；设备必须找到唯一可用锚点。
- **图片源分辨率、源密度和缩放倍率**：描述模板原始像素来自哪里，避免混用不同来源的缩放参数。

表单与 JSON 均可编辑。服务端会验证有限数值、比例范围、区域顺序和必需锚点；非法配置不能保存。页面检测不能把一个固定坐标当成元素存在的证据。

## 新坐标契约

### 位置与偏移分开

位置使用 `position`：

| `position.space` | `x/y` 的含义 |
| --- | --- |
| `screen_normalized` | 相对当前物理屏幕的 0–1 比例 |
| `content_normalized` | 相对当前目标应用可见区域的 0–1 比例 |
| `anchor_normalized` | 相对唯一锚点 bounds 的 0–1 比例 |
| `screen_px` | 当前屏幕像素坐标 |
| `capture_px` | 实际运行时截图的像素坐标，经过捕获尺寸校验与换算 |

`0` 是有效数值；比例 `1` 对应区域内最后一个像素，避免落到屏幕之外。

偏移使用独立字段：

```json
{"offset":{"unit":"dp","x":0,"y":4}}
```

`px` 是屏幕像素，`dp` 随设备密度换算，`target_fraction` 相对目标宽高计算；例如 `x: 0.25` 表示向右移动目标宽度的四分之一。显式 `offset` 优先于旧的偏移字段。

### 语义定位加区域

下面是结构示例。实际范围应根据目标页面确认：

```json
{
  "type": "text",
  "value": "发送",
  "priority": 1,
  "region": {
    "space": "content_normalized",
    "left": 0,
    "top": 0.35,
    "right": 1,
    "bottom": 1
  },
  "offset": {"unit": "dp", "x": 0, "y": 0}
}
```

区域四边必须在 `0–1` 之间，并且 `left < right`、`top < bottom`。区域还会与当前应用可见区域相交，不会允许点击窗口外的另一个应用。

### 锚点内部的相对位置

示例中的资源 ID 是占位符，需要替换为目标手机上实际读取到的容器 ID：

```json
{
  "type": "coordinate",
  "priority": 90,
  "anchor": {
    "type": "id",
    "value": "<实际容器资源ID>",
    "match_mode": "exact"
  },
  "position": {
    "space": "anchor_normalized",
    "x": 0.85,
    "y": 0.5
  }
}
```

有锚点且未另设区域时，默认作用范围就是锚点 bounds。找不到锚点或找到多个候选时返回定位失败，不回退到整屏同名文字。

### 图片策略

```json
{
  "type": "image",
  "template": "send_button.png",
  "threshold": 0.88,
  "source_resolution": "1080x2400",
  "source_density": 3,
  "priority": 50,
  "region": {
    "space": "content_normalized",
    "left": 0.5,
    "top": 0.4,
    "right": 1,
    "bottom": 1
  }
}
```

`source_resolution` 与 `source_density` 必须对应该模板的实际截图来源。这些元数据绑定到所选选择器分辨率配置中的同名文件，包括 `default` 或兼容的其他分辨率配置；其他后备图片根据各自文件名或目录推导来源，不借用这张模板的元数据。上面的数值只说明格式，不是所有手机的通用值。已知密度时优先按密度推导等比尺度；旧文件名中的 `@宽x高` 和分辨率目录仍可提供兼容信息。

通常先不填 `scales`，由设备推导有限候选。若手动填写，它表示对模板像素的**实际倍率**，最多五个，每个在 `0.25–4` 之间，例如 `[0.9,1,1.1]`；它不是对自动推导倍率再次相乘的微调值。匹配失败不会自动降低你设置的阈值。

裁模板时尽量只保留稳定图标或标签，避免包含视频画面、用户名、点赞数字等变化内容。不同来源的图片不能共用未经核实的尺寸元数据。

## 设备脚本调用建议

业务动作优先使用 `uiOperator.clickAction(actionName, timeout)`，让查找和执行使用同一次解析的范围。需读取文字、层级或 bounds 时，`findElement` 仍返回原生无障碍节点。执行前会调用原生节点可用的 `refresh()` 刷新缓存；刷新失败或节点失效时终止操作。

若同一个原生节点被不同范围的查找重复返回，执行器无法从相同的对象引用判断调用方保留的是哪一次结果；此时拆开的 `findElement` / `clickElement` 会拒绝歧义点击。重新使用 `clickAction` 可以按该动作当前配置查找并执行，不会沿用另一动作的范围。

图片、OCR 和坐标结果均有观测时间与几何签名，超过五秒或窗口几何改变后不能直接复用。锚点移动或改变尺寸后，依赖旧锚点生成的点也会失效，即使旧坐标仍然落在新的锚点范围内。出现这些情况应重新定位。

## 旧配置的兼容含义

本次不自动重写数据库中的旧 JSON。已有字段继续按原策略类型读取：

| 旧字段位置 | `x_percent/y_percent` 的含义 |
| --- | --- |
| `type: coordinate` | 相对整屏的 0–1 位置比例 |
| `type: image` | 相对匹配中心的像素偏移 |
| 文本、ID、描述、类名、链式节点 | 相对节点宽高的百分比偏移，`10` 表示 10% |

旧界面中把坐标比例写成“0–100”的说明已更正。不要把所有历史值统一除以 100。旧 coordinate 的位置比例也不会在 `press` 模式再加一次。

需要把旧坐标迁移为应用区域或锚点坐标时，先选择新的坐标空间，再基于实际区域重新确认位置。选择不同空间可能改变同一数值对应的物理位置。

## 标定的变化

自动标定逐动作检查模板覆盖，某一个动作已经有当前分辨率模板，不会让其他动作一起跳过。

采集时要求页面指纹匹配，并找到唯一、稳定且可见的语义目标；当前图片匹配器只返回首个合格结果，不提供唯一性证明，所以仅有图片策略的动作不会据此自动再裁一张图。纯坐标动作也不会被自动转换成“看似正确”的新模板。无法观察到的自绘控件，需要先补充可靠的选择器或人工制作模板。

截图小于物理屏幕时，会先换算目标 bounds 再裁剪；无法解释的长宽比变化会使采集失败。不会直接把屏幕像素当作截图像素。

服务端按来源选择器 ID/版本校验，再按动作、目标抖音版本、分辨率更新配置。来源已被修改时，返回冲突，需刷新配置后重新定位。一个上传批次先整体校验，再保存图片和发布配置；图片以内容摘要命名，避免覆盖其他配置正在引用的旧文件。原动作没有图片策略时会补一条图片后备策略。

旧设备上传缺少来源标识时，仅在来源配置唯一时继续兼容；存在多个可能来源时不会随意挑选一条。新旧设备混用期间，建议一并更新服务端和设备脚本。

## 发送与重试的可见变化

一次点击返回成功只说明执行器接受了操作。当前实现只有在看见新出现的精确消息文字、且输入框已清空时才确认发送；若有新的明确失败标记则记失败，其余情况为待确认。该检查观察的是客户端界面，不是抖音服务器的送达或已读回执；目前也未根据气泡方向证明新增文字一定由本账号发出，需要在目标版本上检查并发来信等情况。

待确认结果不计入成功数，也不会补一次 Enter 或立即重发。新脚本创建的私信占用使用 `pending_confirmation`，服务端保留该记录，管理端显示“发送待确认，已暂停自动重发”。明确成功后恢复正常会话状态；明确未发送的失败仍可释放占用。设备在持有占用后崩溃，也可能留下需要人工核实的记录。

这会使原先被乐观计为成功的部分动作变为“待确认”。若实际版本无法提供可读输入框或消息文字，应先针对该页面完善语义选择器和结果证据；不要通过恢复盲点坐标或重复点击来提高表面成功率。

## 更新顺序

1. 审查并合并本分支 PR。
2. 按项目现有部署方式更新后端并重启服务；本次不新增数据库迁移。
3. 构建并更新管理端：在 `web` 目录运行 `npm run build`，发布生成的静态资源。
4. 更新 Android 设备上的完整 `device/` 脚本目录并重新启动 AutoJS6。若通过服务端脚本更新功能发布，ZIP 根目录应包含 `main.js`、`config.js`、`core/`、`handlers/` 等原有结构；确认包含新模块 `core/screen-context.js`、`core/image-locator.js`、`core/ocr-locator.js`。仅刷新网页不会替换手机上正在运行的脚本。
5. 从一台测试手机开始验证，再扩展到其他设备。已部署服务端兼容旧客户端；新脚本的完整能力需要配套的新服务端。

## 真机验收矩阵

以下分辨率是测试覆盖示例，不表示已经连接并验证了这些手机：

| 维度 | 至少检查 |
| --- | --- |
| 尺寸 | 720×1600、1080×2340、1080×2400、1440×3200 |
| 同尺寸不同显示设置 | 默认/较大显示缩放、默认/大字体 |
| 导航与遮挡 | 手势导航、三键导航、键盘展开/收起、真实弹窗 |
| 布局变化 | 横竖屏、不同抖音版本、目标滑出容器、定位后目标移动 |
| 关键动作 | 搜索框、搜索标签、排序菜单、评论列表、发送、关注 |
| 记录 | 正确目标命中率、实际动作成功率、误点、回退次数、定位耗时；保存对应截图和控件树 |

本次已调整列表内的遍历和滑动；原有个人主页浏览手势仍按物理屏幕计算，尚未全部改为应用窗口内手势，在分屏或小窗使用前仍需单独确认。

自动化测试覆盖坐标数学、真实模块在模拟 AutoJS 接口下的执行、API 与 UI 契约和既有回归测试。没有真实 Android / AutoJS6 / 抖音设备参与测试，也没有新增 OCR 模型或收集实际手机模板。因此，不承诺任意机型或任意抖音版本的识别成功率。
